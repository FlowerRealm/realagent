# ADR-0011: 废除插件 type，能力由实现决定；冲突一律显式

- 状态：已接受，**已被 ADR-0016 取代**（插件系统于 2026-08-25 废除，能力并入 core）
- 日期：2026-08-15
- 取代：ADR-0001「插件类型（type 字段）」一节；ADR-0004「core 据依赖链解析协议链入口」；ADR-0009 的模型重名条款

## 决策

插件能干什么，由**插件的实现**决定，不由元数据里的分类声明约束。core 不问"你是什么类型"，只看"你能干什么"。

1. **删除 `type`**：`plugin_api_t` 的 `plugin_type_t type` 字段、`plugin.json` 的 `type` 键、loader 的声明⇄实现一致性校验、`kTypeNames` 表，全部删除。`GET /plugins` 的 `type` 字段换成 `capabilities` 数组，由非空函数指针派生——**按构造不可能与实现不符**。

2. **能力槽（Capability Slot）**：core 侧每种能力一个指针。协议槽认 `build_request` + `parse_feed` 双非空，权限槽认 `decide` 非空。调用点由「扫全表 + 判 type」变成一次解引用。

3. **槽位独占**：两个插件同时具备同一能力即**加载失败并点名双方**。不后写覆盖，不先到先得。要覆盖别人必须在 init 中 `claim(插件名)` 显式接管，被接管者退出候选集。

4. **命名空间隔离具名条目**：工具 `<插件名>_<工具名>`（Messages API 约束工具名匹配 `^[a-zA-Z0-9_-]{1,64}$`，斜杠点号非法），命令 `<插件名>:<命令名>`。插件名须匹配 `^[a-zA-Z0-9-]+$`——禁止下划线，否则前缀无法无歧义解析。短名由 core 配置 `plugins.unprefixed` 的**名单**决定，不做自动去重。每个条目恰好一个对外名字；最终名字撞车即加载失败。

5. **当前 provider 由配置显式指定**：`provider` 键给出插件名。多个 Provider 壳同时装载时全部初始化，只有被指定的进槽，`/provider` 切换即换指针。未配置时恰好一个候选就用它，多个候选是硬错误——不猜。

6. **模型注册表按 (插件, 模型名) 建键**：多个壳报同一模型是预期行为（同一模型的多条到达路径），不是冲突。

7. **跨边界内存统一 core 分配**：core API 提供 `alloc`，`plugin_api_t` 的 `free` 删除，`list_models` 的"内存归插件"特例取消。

8. **`register_*` 撞名返回 `PLUGIN_ERR`**：原实现一律返回 `PLUGIN_OK`，插件无从得知自己覆盖了谁。

ABI 2 → 3，六个插件全量重编。

## 动机

`type` 从来没有约束过任何东西。加载期只校验 `plugin.json` 的字符串等于 `api->type` 枚举的名字——**从未校验枚举与函数指针是否一致**。后果：

- `type = tool` 的插件填了 `decide`，不会被调用（死代码），但填了 `list_models` **会**被 `register_models` 收录，因为那里只判指针非空。
- `PLUGIN_TYPE_TOOL` 在执行路径上零作用：`execute_tool` 的分发只看 `tool->owner->api->execute_tool`，从不看 type。
- `PLUGIN_TYPE_SESSION` 全仓库零处判断，纯占位。

同时代码里有五处静默冲突：工具名、命令名、模型名后写覆盖（且一律返回 OK），权限插件遍历投票，协议插件 O(n²) 扫描"没被别人依赖的那个"当入口。`type` 只是趴在这套分裂之上的第三层声明。

## 候选方案与权衡

### 能力如何声明

1. **保留 type 枚举** —— 与函数指针构成两套真相，须持续维护一致性校验；新增能力要改枚举、改 SDK、bump ABI。已废除。
2. **字符串键服务注册表（provide/consume + 不透明 vtable）** —— 学 Cordis / DeepSeek Harness 的 `ctx.llm` 模型：新增服务不动任何结构体、不 bump ABI，插件间还能交换 core 完全不认识的能力。能力强，但代价是多提供者仲裁必须逐服务定制（权限全遍历、协议找链入口、工具按名索引、模型合并），把一个特殊情况换成四个。
3. **非空函数指针 + 独占槽位（选定）** —— 能力即实现，槽位即分类。多提供者仲裁问题不是被统一，而是被**取消**：同一能力两个提供者根本不合法。

方案 2 的能力留了后路：真需要动态服务时，`claim` 与槽位机制不阻碍再加一层。

### 装饰关系怎么表达

1. **依赖链推导入口（原 ADR-0004）** —— core 扫全表找"没被任何协议插件依赖的插件"。结果取决于目录扫描顺序与依赖图形状，是典型的静默仲裁；且 O(n²)。
2. **waterfall 中间件** —— 协议层与壳各挂一个带优先级的监听器，core 负责串联，链本身消失。干净，但把编排机器搬进 core，而实际只有一处用得上。
3. **显式 claim（选定）** —— 壳在 init 里写死自己包着谁。读壳的代码即知拓扑，core 不推导。兄弟壳各自 claim 同一个协议层，互不影响。

### 短名怎么给

1. **唯一时自动注册短名** —— 结果随"当前装了哪些插件"漂移：装第七个插件可能让第三个插件的短名突然消失。
2. **core 名单（选定）** —— `plugins.unprefixed` 写下来，不随环境变化。代价是内置工具相对第三方有特权，但**特权是明写的**，不是推导出来的。
3. **全部强制前缀** —— 最一致，但 LLM 见到的是 `core-tools_read`、用户要打 `core:quit`。收益不抵手感损失。

## 后果

**正面**

- `find_protocol_plugin` 的 O(n²) 反查、`depends_on` / `get_dependency` / `assemble_nested`、`kTypeNames` 与声明⇄实现校验、`plugin_type_t` 枚举，全部删除。
- 五处静默冲突消失：三处改为加载失败点名，两处（模型重名、协议入口）因键或槽位重设计而不再发生。
- `GET /plugins` 不可能与实现不符——它是排查任何插件问题的起点，此前会撒谎。
- 跨边界内存只剩一条规则。

**负面 / 代价**

- ABI 2 → 3，六个 plugin.json + 六个插件全量重编。
- 装两个 Provider 壳从"能跑（入口由扫描决定）"变成"必须配 `provider`"。这是刻意的：原先那个"能跑"是靠运气。
- `list_models` 从返回静态字符串变成拷贝一份。

**不变**

- 单入口 `on_event` + 插件内字符串分发（ADR-0001 此项保留）。
- 权限裁决 `PLUGIN_PERM_ALLOW / DENY / ASK` 三值不变——槽位独占后只有一个裁决者，ALLOW 就是字面意思，不存在覆盖他人裁决的单调性问题。
- 无 env 覆盖、无必需键、无热重载（ADR-0010）。`provider` 与 `plugins.unprefixed` 是默认树里的普通键，缺失即取默认值。
- **`plugin.json` 删 `type` 无迁移代价**。boost 的 described-class 解构（`value_to.hpp:400-431`）只遍历已描述成员逐个 `obj.find`，**不比对象大小**——多余的键被静默忽略。残留 `type` 的旧 `plugin.json` 照常加载，真正拦住旧插件的是 ABI 强校验，报"ABI 版本不符"。（`size_mismatch` 那条消息在 described class 里是**缺键**时借用的，见 `value_to.hpp:379`；比大小的是 tuple/array 路径。）

## 配置键落点

默认树（ADR-0010）现有两层：**顶层**是协议链的内容参数（`api_key` / `base_url` / `model` / `small_model`），**`plugins.*`** 是加载与装配（`plugins.disabled`）。新增两键按同一条线放：

- **`provider`（顶层）** —— 在**已加载**的插件里选一个进协议槽。和 `model` 在已注册模型里选一个同性质，`/provider` 与 `/model` 都是运行时选择、都写回 `settings.json`。
- **`plugins.unprefixed`（`plugins.*`）** —— 决定 init 时注册出什么名字，是装配期的事。

判据一句话：**`plugins.*` 决定装不装载，顶层决定跑起来用哪个。** 被 `disabled` 的插件根本不 dlopen；未被选中的 Provider 壳**照常加载并初始化**，只是不进槽——这正是 `/provider` 能不重启切换的前提。
