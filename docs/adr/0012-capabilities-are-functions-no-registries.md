# ADR-0012: 能力是一个函数；管线取代嵌套；core 不建注册表

- 状态：已接受，**已被 ADR-0016 取代**（插件系统于 2026-08-25 废除，能力并入 core）
- 日期：2026-08-16
- 取代：ADR-0004「嵌套链 / 壳包裹协议层」与「构造 + 解析成对」两节；ADR-0011 决策 3（claim 接管）、决策 6（模型注册表复合键）、决策 7（跨边界内存统一 core 分配）、决策 8（`register_*` 撞名返回 `PLUGIN_ERR`）

## 决策

插件是**一组能力的容器**，不是能力本身。**一个能力 = 一个名字 + 一个函数**，零例外。

1. **管线取代嵌套**。一次 LLM 调用由 core 拆成前后相接的几段，每段调一个能力，上一段的产物即下一段的入参：

   ```
   对话 ──生成请求──▶ 粗请求 ──改请求──▶ 精请求 ──[core 发出]──▶ 响应流
                                                             │
          事件 ◀──计价── 事件 ◀──解析响应──────────────────────┘
   ```

   插件**互不认识、互不调用**：改请求的插件收一个请求、还一个请求，不知道请求是谁生成的。于是 `claim`、接管、装饰器、外层/内层、被接管者退出候选集、接管方的连带卸载——全部不再存在。协议层提供"生成请求"与"解析响应"，供应商壳提供"改请求"与"计价"，四段各占各的槽。

2. **"构造 + 解析成对"作废**。它们是管线上两段独立能力，中间隔着 core 的网络往返而已，不构成一个能力。同理，能力名不拆到函数级（查 `protocol.build_request` 与查 `protocol` 本质相同）——每个能力本来就只有一个函数，无从拆起。

3. **能力表取代能力字段**。`plugin_api_t` 收敛为固定五项（`abi_version` / `name` / `init` / `destroy` / `capabilities`），插件经 `capabilities()` 交出一张 `{名字, 函数}` 表。**新增能力 = 新增一个键**：不动结构体、不 bump ABI、不重编无关插件。core 认识的键是有限集，其签名由 SDK 声明并随 ABI 版本固定；不认识的键 core 不解释——那是插件之间的私约。

4. **core 不建注册表**。工具、命令、模型三张表删除，`list_tools` / `list_commands` / `list_models` 现问现答，用完即弃。判据：core 里出现"插件数据的副本"即为跑偏；唯一允许的副本是失效点明写的缓存（状态栏按 `(provider, model)` 备忘）。

5. **两类内存规则**。插件长期持有的（清单、静态表）走**借阅**：`const` 指针，有效期等于插件在位时长，两侧都不释放。本次调用产生的（管线上流动的请求、工具结果）走**转移**：经 `core->api->alloc` 分配、core 释放。判据是"这份数据本来就在插件手里，还是这次现造的"。

6. **依赖是容器级 DAG**。`plugin.json` 的 `deps` 声明容器，不声明能力（如同 mod 依赖 mod，不依赖 mod 里的物品）。按 `deps` 建反图，自入度为 0 起 **BFS 逐层** init；剩余节点即环，点名失败。同一张反图的出边就是"谁依赖我"。

7. **查询让插件按现状决策**。`providers(能力名)` 返回提供者容器名（不含调用者自己）。能力索引在全部 `plugin_create` 之后、任何 `init` 之前建成，因此查询结果与 init 顺序无关，永远完整。

8. **卸载级联**。禁用一个容器时沿反图 BFS 收集依赖者，**逆加载序**先卸依赖者再卸目标。级联停用不写入 `plugins.disabled`（清单是用户意图，级联是推论）；被依赖者重新启用时，凡不在清单内且 deps 已满足者自动重载。

9. **选定 provider 一次定下整条管线**。配置 `provider` 指名一个容器，它提供"改请求"与"计价"；它 `plugin.json` 里的 `protocol` 字段指名协议容器，那个容器提供"生成请求"与"解析响应"。四段零推导、不拼盘。装了多个供应商容器时全部初始化，只有指名的那个上线，`/provider` 切换即换指针——两家都要往请求里塞自己的端点与凭证，串起来的结果只取决于加载顺序，那是被明令禁止的静默仲裁。

   `protocol` 必须由插件作者声明、不可推导：精修代码是照着某个协议的请求形状写的（往 `body.model` 填模型名、往 headers 塞凭证，位置都是协议特有的）。该字段自带一条依赖边，`deps` 不必重复列。也不开放给用户配——用户选的是 provider，不是把某家的精修接到别的协议上。

10. **管线的段数明写在 core 流程里，不引入通用钩子**。新增一段（如上下文压缩）要改 core：加一个能力名、加一次调用；但 `plugin_api_t` 不动、ABI 不变、已有插件不重编（能力表里没这个键，core 查不到即跳过）。

11. **槽位冲突改为"空置并点名"，不卸载插件**（修正 ADR-0011 决策 3 的"加载失败点名双方"）。两个容器同时提供权限裁决，是**配置问题**不是插件坏了——卸载它们既救不了这一槽，还会连带损失它们的其它能力。空置的效果同样响亮（dangerous 工具一律拒绝），且用 `plugins.disabled` 禁掉一个即恢复。

12. **`import` 供插件之间取用能力**：`import(容器, 能力名)` 取一个函数 + 对方实例，目标须在自己的 `deps` 内。这不是接管——对方照常参与管线。core 不认识的键就靠它交换，签名是双方私约，core 全程不解释。

ABI 3 → 4，六个插件全量重编。

## 动机

ADR-0004 让供应商壳**包住**协议层：壳持有内层接口表，`build_request` 调内层再改，`parse_feed` 转发内层事件并按需拦截。ADR-0011 为这套包裹关系配了 `claim`（显式接管 + 退出候选集）。整套机器只为一件事：**让壳有机会在请求发出前改它**。

而那件事只需要"收一个请求、还一个请求"。改成管线后，接管、候选集、连带卸载、"半个协议能力"、装饰点该放在数据还是放在 io——一整类问题连同它们的机器一起消失。

同时 ADR-0011 把能力落在 `plugin_api_t` 的非空函数指针上：每加一个能力就要加字段、bump ABI、让所有插件重编并为不提供的能力显式填 `nullptr`——正是它自己否决 `type` 枚举时给出的理由。函数量随能力数增长，且 core 必须预先认识每一个能力。

core 还收藏了三份插件数据。为维护这三份副本存在的机器——`register_*` 两个 API、三种 Entry、撞名记账、`unregister_entries`、模型的 `(插件, 模型名)` 复合键、加载期的二次严格校验——全部只服务于"副本要与真相同步"。数据留在插件里，这些一并消失。

## 候选方案与权衡

### 壳怎么改请求

1. **包裹（ADR-0004）** —— 壳持有内层引用逐层改。需要接管机制、候选集管理、连带卸载，且"装饰点"始终没有好位置：放在构造出的三个字符串上，所有权来回搬；放在 io 拦截上，要给 core 加一套 HTTP 原语并控制反转。
2. **合并成一个 `turn()`，插件自带 HTTP** —— 能力确实变成一个函数，但每个供应商各写一遍超时/代理/证书/重试，横切策略一分散必然漂移；且推翻"网络传输 core 内置"的既定分工。
3. **管线（选定）** —— 粗请求进、精请求出。插件互不认识，接缝天然存在，core 保持对网络的统一控制。

### 能力怎么表达

1. **结构体字段（ADR-0011）** —— 类型安全，但函数量 O(能力数)，每次加能力破 ABI。
2. **能力子结构指针** —— 膨胀从函数挪到字段，仍每次破 ABI。
3. **能力表（选定）** —— 键是字符串，`plugin_api_t` 永久固定。转型集中在提取器一处（每容器每能力一次），调用点拿到的仍是强类型槽。代价是键写错等于能力静默消失——加载期扫出 core 不认识的键即警告（不失败：新插件在旧 core 上多报的能力应被忽略）。

ADR-0011 曾以"多提供者仲裁必须逐服务定制"否决字符串键方案。该理由针对仲裁，而仲裁已由能力槽取消；core 只对自己认识的键仲裁，其余键连形状都不知道。参考 DeepSeek Harness / Cordis 的服务模型（字符串键 + `inject` 依赖 + effects 回滚）：键的部分可借鉴；effects 回滚不需要——push 注册才要记住怎么撤销，pull 没有东西可撤。

### core 参与的步骤怎么扩展

1. **waterfall 中间件（DeepSeek Harness 的做法）** —— 生命周期钩子（`agent/pre-step`、`agent/request`、`tools/result`）上挂监听器，签名 `(args, next)`，调 `next()` 继续、不调即短路整条链。加新步骤不改框架。但"经过哪几段、什么顺序、谁短路了谁"变成运行时才知道，而顺序决定结果——正是本项目一路在消灭的隐式仲裁（ADR-0011 亦以"把编排机器搬进 core，实际只有一处用得上"否决过）。
2. **固定管线（选定）** —— 段数明写在 core 流程里，读代码即知一次调用经过什么。代价是加新段要改 core 一次调用；换来的是流程可读、顺序不可能隐式。将来若真需要横切插手（日志、trace header 这类**不抢身份**的），另开一个可叠加的能力键（如 `request.intercept`），顺序按 DAG 拓扑序——那是声明出来的，不是加载顺序碰出来的。

### 依赖的粒度

1. **能力级** —— 换实现不改声明，但同一容器会以它各个能力的名义在 `deps` 里反复出现，边被打散成线团。
2. **容器级（选定）** —— 与 mod 依赖 mod 同构，边少、可读、天然成 DAG。依赖保证存在，查询回答内容。

## 后果

**正面**

- 嵌套链、`claim`、接管候选集、连带卸载、装饰点选址——整类问题连同机器一起删除。
- `plugin_api_t` 从"随能力增长"变为固定五项；新增能力零 ABI 改动，插件间可交换 core 完全不认识的能力。
- 三张注册表及其同步机器消失（`register_*`、三种 Entry、撞名记账、`unregister_entries`、复合键、二次校验）。
- 加载期首次具备**环检测**（Kahn 剩余节点），此前遇到环是"剩余强制加载"。
- 卸载被依赖者不再产生悬垂引用（此前 `disable v1-messages` 会让 deepseek 握着已 `dlclose` 的接口表，下一次对话段错误）。
- `core-tools` 的 `bash` 输出缓冲不再泄漏（改为 core 分配、core 释放）。

**负面 / 代价**

- ABI 3 → 4，六个 `plugin.json` + 六个插件全量重编。
- 能力键写错不再有编译器兜底，靠加载期未知键警告。
- 粗请求要在 core 与插件之间多走一趟（生成 → 改），比原先壳内直接改多一次跨边界传递。这是把"包裹"换成"传递"的固有成本，换回的是整套接管机器的消失。

**不变**

- 能力槽与槽位独占：每段管线只有一个执行者，冲突点名，不猜。
- 命名空间前缀与 `plugins.unprefixed` 名单、`provider` 顶层键、`/provider` 免重启切换。
- 单入口 `on_event` + 插件内字符串分发；无 env 覆盖、无热重载（ADR-0010）。
- 计价留在供应商侧，token 不上传 core（ADR-0009）。
