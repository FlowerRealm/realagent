# ADR-0023：Provider 作为一束配置回归；配置树长出第一层嵌套

- 状态：已采纳（2026-08-29）
- 部分取代：ADR-0010（「配置树是平的」这一句；`persist` 点对点的原则保留）
- 补充：ADR-0017（端点束仍然没有默认值，只是换了住处）
- 部分取代：ADR-0017 §2（缺键要不要拦；「不在启动时退出、但每次 `POST /message` 原样回那段话」那套机制）
- 不复活：ADR-0004、ADR-0016（Provider **壳**仍然是死的，本 ADR 不把它挖回来）

## 背景

需求是一条 `/provider` 命令，让用户在 TUI 里配模型后端，不必手改 JSON。

第一个要回答的不是「怎么做」，是 **「这不就是 ADR-0016 铲掉的 Provider 壳吗」**。

不是。区别与 ADR-0022 用过的那把尺子一样——**core 里有没有多出一条执行路径**：

| | ADR-0004 的 Provider 壳 | 本 ADR 的 Provider |
| --- | --- | --- |
| 是什么 | 一个动态库，有 `init` / `refine_body` / `refine_headers` | 配置文件里的一个 JSON 对象 |
| core 里的执行路径 | 每次调用都要过它三道手 | 零。读配置而已 |
| 知不知道对面是哪家 | 知道（`deepseek.cpp` 里写死端点与模型名） | 不知道，也没地方知道 |
| 计价 | 壳负责，且要跨调用记账 | 不参与（[[模型数据表]]的事） |

壳是**代码**，这次是**数据**。同名不同物。

今天的实际约束：配置树顶层五个键（`protocol` / `base_url` / `api_key` / `model` / `small_model`），
改任何一个都得手开 `settings.json`。而这五个键恰好是**共变的一束**——换后端就是这五个
一起换——却散在顶层，跟 `permission` 这种毫不相干的键混在一起。

## 决策

### 1. Provider = 端点束 + 凭证 + 模型清单，一个对象

```json
{"provider": {"protocol": "anthropic-messages",
              "base_url": "https://rightapi.ai/deepseek/anthropic",
              "api_key": "sk-…",
              "models": ["deepseek-v4", "deepseek-v4-flash"],
              "model": "deepseek-v4-flash",
              "small_model": "deepseek-v4-flash"}}
```

**盘上就这一份。** 换后端就是把这一束的字段改掉，没有「哪一份生效」这个问题——
于是也没有列表界面、没有切换动作、没有增删，`active_provider` 这个键根本不存在。
[[Model（模型元数据）]]条目里「一次运行只有一个 `base_url`」那条不变量因此是**结构上**
成立的，不再靠一条规矩维持。

**它没有名字。** 名字是用来在多份里挑一份的，只有一份就没有可挑的。

**两档选中的模型名存在 provider 内部，不在外面。** 否则换完端点之后那个名字可能不在新
清单里，于是要么静默发一个对面不认的模型名（ADR-0017 §4 刚治过的那类病），
要么补一段「换的时候校验并回落」的逻辑。装在里面，这个情况不存在。

### 2. 配置树长出第一层嵌套

```json
{"provider": { … }, "permission": "ask"}
```

顶层的端点五键**消失**。ADR-0010 写着「配置树是平的（ADR-0016 删掉 plugins 那一节之后
再没有嵌套键），所以不必递归——**需要嵌套的那天连着默认树一起加，不提前留机械**」。
那天到了，机械现在加。

`merge_into` **仍然不递归**：那一束的语义正是「一起换」，整个替换就是对的。
默认树里没有 `provider`，所以也没有可合并的东西。

`permission` 留在顶层——它不属于那一束端点配置。

### 2b. 没有任何一处校验配置齐不齐

ADR-0017 §2 定了两件事，这里只留前一件：

1. **端点那一束不给默认值**——保留。core 不替用户猜。
2. **缺了就在 `POST /message` 上拦住，把该配什么一次说全**——**删掉**。

`endpoint_config_error()` 整个函数、它在启动日志与 `POST /message` 上的两个调用点，
一并删除。缺了什么就让它**以本来的方式**失败：空 `base_url` 换回 libcurl 一句
URL 格式错，端点不认的模型名换回一个 400，缺 `api_key` 换回一个 401。

理由是这些失败本来就有话说，而校验器说的是**另一套话**——两套话迟早对不上。
ADR-0017 当初担心的「填错产生的报错最难自己诊断」，治法是不给默认值（别让用户
以为自己配对了），不是再加一个前置的判官。

**一趟里抛出来的东西也不该杀掉 core**：agent 跑在自己的 `std::thread` 上，
这条线程上没有别人接着，漏出去就是 `terminate`——上机验过，配置里把 `base_url`
写成个数字（`8080`）就足以让整个常驻服务当场死掉。现在那一趟收口成「这趟失败」，
core 照常活着。

**唯一的例外是 `protocol`**：它不失败。它决定请求长什么样，解不出来就没有「一个请求」
可谈——`build_request` 从前在这儿 `value()` 硬解，解不出来 throw，会 terminate 整个
常驻服务。现在协议由调用方解析好传进 `build_request`，解不出来时**那一趟**失败
（说明只有哪三个值），core 照常活着。这不是校验，是那一趟走不下去。

代价：**配了一半的时候，第一次失败发生在真发请求那一刻**，而不是发消息那一刻。
换来的是只有一处在回答「哪里不对」。

### 3. 取值用 JSON Pointer

```cpp
req.url = cfg.get("/provider/base_url") + "/v1/messages";
```

一行。路径自己说清读的是哪儿，`Config` 那头是一句 `settings_.value(json_pointer, "")`。
`_json_pointer` 是 nlohmann 自带的，本仓库在 `http_status_error()` 里早就在用
（`j.value("/error/message"_json_pointer, …)`）——**这里没有任何需要自己写的东西**。

到这一步之前绕过两次弯路，两次都是自己造壳，记在这儿免得后人再走一遍：

1. **`is_provider_key()`**——一张「哪五个键住在 provider 里」的名单，`get()` 每次比一遍
   然后转向。它的好处只有搬键那天调用点一个字不用改；迁完就变成常驻的隐式跳转，
   `get("base_url")` 与 `get("permission")` 在调用点长得一模一样、读的却是两个地方。
   而那份名单是第二份真相——数据本身已经说了它们在哪儿。
2. **`provider_get(field)` / `provider().value(field, "")`**——前者是薄壳，后者一个 URL
   要写两行（先拷一份出来再取），还得回答「拷贝要不要复用」这种不该存在的问题。

**`provider()` 保留**，但只服务一个真需求：`/provider` 与 `/model` 的回包要把整束交出去。
它**按值返回**——`settings_` 在 mutex 后面（agent 线程读的同时事件循环可能正在写），
交出引用就是交出一个没上锁的引用。这也是这里不能直接暴露 `cfg["base_url"]` 的原因；
顺带，nlohmann 的非 const `operator[]` 对不存在的键会**插入一个 null**，拿它读配置
等于边读边改。

**没配就给空对象，不是 null**：`null.value(...)` 会抛，而「没配 provider」是第一次启动的
默认情况。「没配」与「配了但这个字段是空的」对下游本来就是同一件事。

**`Config::has()` 一并删掉**：全项目零调用者。

### 4. 不写迁移代码，不做兼容读

老格式（顶层端点键）在新 core 眼里就是未知键，被无视，然后 `endpoint_config_error()`
照常喊缺键。**全世界只有一份老配置，手改一次即可**，为它写代码是给一个只会跑一次的
路径留永久维护成本。

顺带保住一件事：core 不会未经请求去重写用户的 `settings.json`（里面有 api_key）。
ADR-0010 §5 的那条边界不因本 ADR 挪动。

### 5. `/model` 的候选来源换成 provider 的 `models`

今天 `cmd_model` 校验「名字在不在 `models.json` 里」。换成「在不在 provider 的 `models` 里」。

**净效果是删依赖，不是加依赖**，而且 CONTEXT.md 那句「**表是参考资料，不是白名单**」
第一次名副其实了：白名单换成了用户自己在 provider 里写下的那几行，`models.json` 退回它
唯一该管的事——「这个模型是什么货色」（`owned_by` / `context` / 单价）。查不到就只剩名字、
算不出钱，正是 `statusline_payload` 今天已有的行为。

`/model` 同时扩成清单的管理入口：加一个模型名、把某个名字设为主档或小档、从清单移除。
**不新开 `/models`**——两条差一个字母、语义高度重叠的命令，人和模型都会选错。

### 6. 命令载荷从字符串扩成结构化 `data`

`POST /command` 的体加一个可选字段：

```json
{"command": "/provider", "data": {"provider": { … }}}
```

**没有子动词**：命令按「带了什么」分——带 `data` 就是覆盖写，不带就是把当前这一束
回给客户端。多一个动词就多一处「用户打的动词与他带的载荷对不上」要处理，
而那个情况本来不存在。

原因是表单：几个字段在 TUI 里已经是分好的字符串，序列化成一行文本再让 core 解析回来，
中间凭空多出一整套引号规则——`api_key` 里可以有空格，`base_url` 里可以有 `=`。
**那些不是边界情况，是编码往返自己制造的。**

`panel.go` 文件头那条「确认 = 把 submit 写进输入框走 `submitInput`，没有第二套提交逻辑」
**要跟着改**，不能留着说谎：`submit` 从此有两种形态（文本命令 / 结构化载荷）。
它真正在防的是**两处各自处理发送、`awaiting`、面板续开**，那一条仍然成立——
发送仍只有一处，只是载荷多了一种形状。

### 7. 写回是整体覆盖 `provider` 那一个键，不是通用 config patch

TUI 拼出**完整的一束**发回来，core 覆盖那一个键。core 不合并、不重算——
所以客户端发的必须是完整的目标状态，改一个字段也得把其余字段原样带上。

不需要新端点：`/provider` 无参的回包本来就带 `data`（`/model` `/resume` 今天就是这样）。
`Config` 为此多一个读访问器 `provider()`，不走 `to_json()`——命令要的是那一个键，
不是整棵树，交出整棵树等于把 `permission` 一类与这条命令无关的东西也送出门。

**`/provider` 与 `/model` 回同一份载荷**：`{provider, models}`，客户端拿它渲染两个
不同的面板（一张表单、一列清单）。分成两份的话，`/model` 那头就看不见 provider 的
其余字段，也就拼不出完整的一束发回来——那会逼 core 重新长出一段合并逻辑。

**core 不再自己校验一遍。** 落盘就是把客户端发来的那两个键原样写进去。

理由是：「这份配置能不能用」本来就有 `endpoint_config_error()` 在答，而且答得更好——
`protocol` 不认识、端点没配齐，它一次说全，还附一段照抄就能改对的样例。再写一个校验器
就是两份真相，而两份真相里迟早有一份先过期。真正被校验器挡住、而 `endpoint_config_error()`
看不见的只剩两种（provider 重名、选中的模型不在 `models` 里），代价是四十行常驻代码
外加一份会与 `llm` 那头漂移的协议名清单——不划算。

**但落盘只认 `provider` 这一个键。** 这不是校验，是范围：客户端发的是那一束端点配置，
不是整棵配置树。放开的话 `/provider` 就能顺手改掉 `permission`——那是安全默认，
不归这条命令管。

### 8. TUI：列表 → 二级菜单 → 表单，一套形状

`/provider` 与 `/model` 共用同一套交互，用户学一次：

- `/provider` 就是一张表单，三格（`protocol` / `base_url` / `api_key`）加一个【保存】。
  **没有列表、没有二级菜单**——只有一份东西，没有「选哪一个」这件事。
- `/model` 是清单：`↑↓` 选、`Enter` 进二级菜单（设为主档 / 设为小档 / 从清单移除），
  末尾一项「+ 新增模型」。**不设隐藏快捷键**。
- 表单：`↑↓` 换行、`←→` 移光标、`Enter` 下一格、【保存】上 `Enter` 存盘、`Esc` 放弃。

**不新造 `form` 类型。** 面板今天是「一列东西 + 一个高亮下标」，表单也是——同一个形状。
`panelItem` 加一个可选字段：

```go
ed *editor // nil = 可选项（Enter 提交 submit）；非 nil = 输入格（Enter 跳下一格）
```

`input.go` 的 `editor` 是自足值类型（`{runes []rune, pos int}`），可以随便实例化，
**不需要引入任何 widget**。一张表单里于是能混着输入格与可选项——`protocol` 那格是三选一，
三个值从 core 的回包里拿，TUI 不留第二份硬编码。

**上下键永远换项，左右键永远移光标**，所以不需要「选择态 / 编辑态」两个模式，
也就没有模式切换键。

## 候选方案与权衡

### 要不要支持多份 provider

1. **一个 `providers` 数组 + `active_provider` 指针（一度实现过）**——能存多套后端换着用。
   代价不是那个数组，是它牵出来的一串：列表界面、二级菜单、切换动作、删除动作、
   「删掉的正好是活动那份该怎么办」、「`active_provider` 指向不存在的名字怎么办」、
   provider 要有 `name` 且不能重名、两个键必须原子地一起写。
2. **就一个 `provider` 对象（选定）**——上面那一串**一条都不存在**，不是被处理掉了，
   是没有地方长出来。换后端就是改这一束的字段，而换后端本来就是低频操作。

### 端点那一束住在哪儿

1. **散在配置树顶层（原状）**——五个共变的键跟 `permission` 混在一起，
   谁也看不出它们是一束。
2. **收进一个 `provider` 对象（选定）**——`get()` 下探那五个键，读取点一处不改；
   写回只碰一个键，`permission` 碰不到。

### 模型清单归谁

1. **`models.json` 按 provider 归属**——条目要加 `provider` 字段，于是同一个模型走两条路径
   就有两条同名条目，而 `name` 是 `Pricing::cost()` 的主键，立刻不唯一。
2. **每份 provider 一个 `models.json` 文件**——清单干净了，但单价在 N 份文件里复制 N 遍，
   ADR-0009 的「存在即整表接管，不合并」要重新定义。
3. **清单进 provider，`models.json` 只管元数据（选定）**——两个问题（「有哪些模型」
   与「这个模型是什么货色」）两处数据，都不必改主键。

### 写回的形状

1. **通用 `POST /edit_config`（按路径写 JSON）**——拒绝，三条理由：
   （a）**它没有边界**。具名命令能写哪几个键，钉死在代码里，也写在这份 ADR 里；
   一个按路径写的端点能碰到配置树的任何角落，`permission` 那种安全默认也在内。
   选定方案同样不做业务校验，区别正在这里：**范围是钉死的，校验才是可以省的**；
   （b）它让「哪些配置能改、改成什么形状」变成运行时才知道的事，正是 [[管线]] 条目
   「不引入通用钩子/中间件机制」与 ADR-0012 拒绝过的东西；
   （c）要传「位置」就要发明路径语法，随之而来一整类新错误（路径不存在、类型不匹配、
   下标越界），而具名命令一个都没有。
2. **整棵 config 覆盖**——拒绝：TUI 手上那棵是合并后的树，发回来会把 `permission: "ask"`
   这类默认值写进用户文件（ADR-0010 §5 明确不要），会抹掉 core 还不认识的键，
   并发覆盖的影响面也扩到整个配置。
3. **只覆盖 `provider` 一个键（选定）**——「一次表达完整目标状态、core 不做合并」全在，
   三条代价一条不沾。而且**不需要新原语**：`Config::persist(key, value)` 本来就是
   点对点写一个键，值恰好是那个对象。

### core 要不要自己校验一遍

1. **校验（一度实现过，四十行）**——`protocol` 三选一、两档选中的必须在 `models` 里，
   外加一串只有多份 provider 才需要的检查。前一条与 `endpoint_config_error()` 重复，
   还得在 command 层再抄一份协议名清单。
2. **不校验（选定）**——落盘只管落盘。判据是：**只有一处回答「这份配置能不能用」**。
   代价是「provider 重名」与「选中的模型不在清单里」失去本地拦截——前者由
   `active_of()` 取第一个命中项，行为确定；后者会换回端点一个 400，而这与
   ADR-0009 早就定下的「core 不校验用户配的模型名，表是参考资料不是白名单」
   是同一个口径。`/model <name>` 那条老用法仍然拒绝清单外的名字：它本来就拒，
   而且那条路径 core 已经在读那份 provider，顺手看一眼几乎不要钱。

### 表单怎么输入

1. **`key=value` 文本参数 + core 写分词器**——在「没有表单」的前提下成立；有表单之后是纯亏损
   （见决策 6）。
2. **TUI 加多字段表单（选定）**——代价一度被高估：`editor` 可实例化，不需要 widget 库。

## 代价与保留

- **`api_key` 明文经 QUIC 往返。** 清单回包带真实 key，TUI 原样拼回来。判据与
  「命令行回显进 scrollback」那次一致：同一个用户、同一台机器、它本来就明文躺在
  `~/.realagent/settings.json` 里，不新增暴露面。保守做法（打码 + 哨兵值回填、
  留空即不改）被评估过，代价是一套哨兵约定，收益只有「TUI 内存里不躺明文 key」。
  **如果哪天 core 要跨机器服务，这一条第一个作废。**
- **并发覆盖会丢更新。** 两个客户端同时开着 `/provider` 表单，后保存的抹掉先保存的。
  影响面限于 `provider` 这一个键（不是整棵配置树），而配后端是低频操作，
  不为它引入版本号或 CAS。
- **配置树不再是平的。** `merge_into` 的语义要为 `provider` 明确写下（对象整个替换），
  测试要盯住它。这是 ADR-0010 预留的那条路，不是意外。
- **换不了后端来回试。** 想在直连与中转之间来回切，只能改字段或手工留几份文件。
  这是「不做多份」直接换来的：省掉的那一串分支与那层界面，代价就是这个。
  真需要来回切的那天，加回一个数组是往上长，不是推倒重来。
- **`/provider` 与 `/model` 之间有一条隐式顺序**：第一次配完 provider 时 `models` 是空的，
  得接着开 `/model` 加一个才能用。缓解是首次保存（原本 `base_url` 为空）后自动顶出
  `/model` 面板，不是在 core 里塞一段自动填充。

## 迁移

**不写代码。** 全世界只有一份老配置，手改：

```json
{
```
