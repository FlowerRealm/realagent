# ADR-0018：`edit` 改为行号加行 hash，废除 `old_string`

- 状态：已采纳（2026-08-28）
- 部分取代：ADR-0002（后果一栏「无文件级互斥需求」那一句）
- 依赖：ADR-0016（工具并入 core，`tools.cpp` 是唯一实现）

## 背景

多 agent（ADR-0019）让「两个 agent 动同一个文件」从不可能变成常见用法，于是重新审了一遍 `edit`。

审出来的问题有三个，其中两个在单 agent 时代就在：

| | 症状 | 位置 |
| --- | --- | --- |
| 改错行且静默 | `content.find(old_s)` 取**第一个**匹配，不检查唯一性。模型说「把 `return 0;` 换掉」而文件里有五个，第一个被改，返回 `edited` | `tools.cpp:89` |
| 陈旧内容无从察觉 | 模型在第 1 轮 `read`，第 5 轮基于记忆里那份内容写别处的代码。文件在这期间被改过——另一个 agent 改的、人用编辑器改的、`git checkout` 换的——它无从知道 | 概念缺失 |
| lost update 的窗口 | `do_edit` 里「读进内存 → `find` → `truncate` 写回」三步之间无保护 | `tools.cpp:69-95` |

第三条**判定为假想威胁，不修**。两次 `edit` 之间隔着一次 LLM 调用（秒级），撞进同一个几十微秒的窗口的概率不构成工程问题。为它加一把锁是在解决不存在的问题。

第二条才是真问题，而且**通知机制解不了**：core 可以记「哪个 agent 最后写了哪个文件」并在变更时通知邻居，但那张表天生漏掉人为修改、`git checkout`、格式化钩子。**只有内容本身能回答「这文件还是我以为的那个样子吗」**。

## 决策

**`edit` 改为内容 hash 寻址（anchor），`old_string` 废除，两者不并存。**

### 1. 一行的 hash

`read` 每行印 `行号 hash 正文`，`edit` 收 `line` 与 `hash` 两个字段——**两个值，不拼成一个串，因此没有解析这回事**。

hash 是 **FNV-1a，取 3 个十六进制字符**（`core/src/tools/tools.cpp` 的 `hash_line`，六行）。算的是**这一行本身**，空白不参与——跑一遍格式化不该让它变（本仓库一个月内真发生过一次，见 `.git-blame-ignore-revs`）。

**不带邻域、不防撞、不做全表 anchor、不做全文回捞。** 起草时这四样都写过，实现时全部砍掉，它们互为因果：

- 带邻域 → 改第 1 行会让第 2 行的 hash 作废 → 同一批里的相邻行必然失败 → 得引入「先全校验再一次写」的两阶段 → 得把 edit 按文件分组、算范围、查重叠、排序。
- 全文回捞（行号漂了按 hash 找）→ 要求 hash 全文唯一 → 要求探测分配 → 要求先算出整个文件的 anchor 表。

**去掉邻域，这一整串全部消失。** 判断只有一句 `if`：按行号取那一行，算它的 hash，一致就改，不一致就报错让模型重读。逐条应用天然正确，因为改第 1 行不影响第 2 行的 hash。

代价照记：文件别处增删行会让行号漂移，那些 hash 一律作废，模型得重读一次。这不是缺陷，是「不做回捞」的定价。

**不用第三方哈希库**，也不用 `std::hash`（标准不保证跨进程稳定，而 hash 会活在模型的对话历史里跨 core 重启）。六行看一眼就知道对不对的代码，胜过四十行只能靠信心的 xxh32。

### 2. `edit` 只有一个操作：把第 `line` 行换成 `new_text`

```cpp
edit_one(e):  if (hash_line(lines[line-1]) != e.hash) 报错
              else 改这一行
do_edit(es):  for (e : es) edit_one(e)     // 遇错即停
```

四种用法，不是四个操作：

| 用法 | `line` | `new_text` |
| --- | --- | --- |
| 替换一行 | 给 | 非空 |
| 换成多行 | 给 | 带换行 |
| 删除 | 给 | 空串 |
| 创建 / 覆写整个文件 | **不给** | 内容 |

最后一行保住 `write` **继续不单独存在**。参考实现（`hashline` / `dsh-better-edit` / hermes-agent 提案）都另留了一个 `write` 工具，本项目不跟。

`edits` 是一个数组，每条自带 `file_path`——**一次调用可以跨多个文件**。

```json
{"edits": [{"file_path": "foo.cpp", "line": 142, "hash": "29c", "new_text": "..."}]}
```

**逐条执行、遇错即停、允许部分应用。** 报错说清停在第几条、前面写入了几条——模型要准确知道停在哪，含糊的报错会让它猜，猜错就是二次破坏。

### 3. 不限大小、不截断、不分页

`read` 读整个文件、原样返回。起草时写过 4MB 上限、50KB 输出截断、`offset`/`limit` 分页、「还有 N 行」提示——**全部砍掉**：本地读一遍内存，限制的是不存在的问题。（`bash` 的 50KB 截断保留，那条是管道，性质不同。）

### 4. 显示归客户端

**今天 `read` 的内容根本不推给客户端**：`emit_output` 只在 `do_bash` 的读循环里调用，`read` 不发 `tool_output` 帧，用户在 TUI 里只看得到 `tool_execution_end` 那一行 `read ✓`。所以行号与 hash 现在不会出现在任何人眼前。

规划中的 verbose 模式要做的正是让 `read` 也发 `tool_output`。那时 core 只发一份原样的输出，客户端决定怎么显示——依据是本项目已有的那条线：「展示偏好纯客户端状态，core 不认」。

`dsh-better-edit` 在这里的解法是另开一个 `read_skill`（无前缀的纯文本读），本项目不跟——那让工具从 3 个变 4 个，模型每次还得选用哪个。

## 参考实现对照

| | 寻址 | 操作数 | hash 算什么 | 重复行 | 创建文件 |
| --- | --- | --- | --- | --- | --- |
| [hashline](https://github.com/quangdang46/hashline) | anchor | 4：`SWAP`/`DEL`/`INS.POST`/范围 | 单行 | **拒绝**，让模型加行号限定 | 另有 `write` |
| [dsh-better-edit](https://github.com/Rianico/dsh-better-edit) | anchor | **1**：`[起, 止, 新文本]` | 单行，去空白 | **探测**，唯一性由构造保证 | 另有 `write` |
| [hermes-agent 提案](https://github.com/NousResearch/hermes-agent/issues/358) | anchor | 3：`set_line`/`replace_lines`/`insert_after` | 单行 | — | 另有 `write_file` |
| [pi-hashline-context-edit](https://www.npmjs.com/package/pi-hashline-context-edit) | anchor | — | **本行 + 前后各一行** | 邻域天然区分 | — |
| **本 ADR** | **`line` + `hash` 两个字段** | **1** | **单行，去空白** | **不管**（按行号定位，别处撞不撞无关） | **`edit` 不给 `line` 的用法** |

**三个实现都没有 `old_string`**，这条有实证。**三个都另留了一个 `write`**，本项目不跟。

三个实现（以及本 ADR 的初稿）都把 hash 算成某种上下文——单行 + 全表唯一，或本行加前后两行。本项目**只算这一行**：上下文进来是为了支撑「按 hash 查找」和「察觉近处改动」，而按行号定位之后，前者不需要，后者由行号漂移天然覆盖。

## 代价与保留

**每次 `read` 每行多几个字节的 token 税**（`142 29c ` 七八个字符）。换来的是编辑失败率下降——**这个数我们没测过**。按 ADR-0017 结尾那条规矩，把话记在这里：如果将来有数据表明失败率没降、或者降的那点不抵这份成本，那就该按同一把尺子把它删掉，退回 `old_string`。

**hash 取 3 个十六进制字符（4096 种取值），够用。** 它不需要在全文件里唯一——判断只发生在行号指定的那一行上。撞上的后果是放过一次本该拒绝的 edit，不是改错行；而要撞上，得是「这一行被改成了另一个恰好同 hash 的内容」，1/4096。**这是 agent 场景，不是密码学场景。**

**`old_string` 有一点确实比这个方案好，这里承认**：它是明文，模型不需要先 `read` 就能写出一条 `edit`。行号加 hash 强制「先读后改」。这是真实的一次额外工具调用，换来的是「改错行」与「改在过期内容上」两类静默错误的消失。

**跨进程的文件锁（`flock`）不做。** 用户拿 vim 在旁边改同一个文件仍可能与 agent 互相覆盖——但那在单 agent 时代就是这样，不是多 agent 引入的，也不是本 ADR 要解的。anchor 只保证「模型知道自己看的是不是最新的」，不保证「没有人同时在写」。

**ADR-0002 后果一栏那句「无文件级互斥需求（不会同 agent 内并发写文件）」不再成立**——多 agent 之后两个 agent 可以拿到同一个 workdir。但结论是**仍然不加互斥**，理由见「背景」第三条：那是假想威胁。ADR-0002 那句话的前提没了，结论碰巧还对，这里把它重新记在正确的理由上。

## 迁移

`edit` 的参数 schema 整个换掉（`old_string` / `new_string` → `edits` 数组，每条带 `line` / `hash`），`read` 的输出每行多一个 `行号 hash ` 前缀。两者都在 `core/src/tools/tools.cpp` 的静态表里，**没有第三方使用者**（ADR-0016 之后工具不再是插件），所以这是一次纯内部改动。

已有会话的历史里躺着旧格式的 `read` 结果与 `edit` 调用。它们**原样保留、不迁移**：那是记录，不是缓存（见 CONTEXT.md [[Session]]）。恢复一段旧会话后模型会看到旧格式的历史与新格式的工具描述——它读得懂，因为新描述在 system prompt 里是当前有效的那一份。
