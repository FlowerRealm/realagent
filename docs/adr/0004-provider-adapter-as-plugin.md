# ADR-0004: LLM 请求构造走插件机制（Provider 适配插件化）

- 状态：已接受（嵌套结构 + 组装机制 + 响应解析均 2026-08-09；协议/供应商拆分 2026-08-10）
- 日期：2026-08-09

## 决策

LLM 请求构造不在 core 内置，而是**插件职责**。管线分四步：

1. core 收集完整对话信息（消息、工具、系统提示词、模型参数）。
2. **协议层插件**按目标协议构造请求体（`/v1/messages`，多家公司共用）。
3. **供应商壳**兜底该供应商的默认配置（端点/模型/凭证），不做协议改写、不做模型映射。
4. core 发出请求。

## 调研对标

| 项目 | Provider 抽象方式 | 对比 |
|---|---|---|
| **Pi** | `pi-ai` 包：统一多厂商 LLM API（OpenAI/Anthropic/Google 等），内置在核心 | 多厂商适配内置于核心包 |
| **OpenCode** | Provider 接口 + factory（`NewProvider(model, options)`），OpenAI/Anthropic/Gemini/Bedrock 等 10+ 后端 | 多厂商适配内置于 core |
| **Codex** | `model-provider` crate + `backend-client`，Ollama/LMStudio/ChatGPT 集成 | 多厂商适配内置 |
| **Goose** | Provider trait 抽象，15+ providers | 多厂商适配内置 |

本项目反其道：**厂商差异是扩展点，不是核心**。core 只负责编排与传输，协议格式和供应商特化全部外置为插件。理由：

- 保持 core 极简——core 不内置任何具体协议知识。
- 厂商差异演进（新供应商、字段调整）不触碰 core，不破坏扩展接口。
- 与 ADR-0001（C ABI 扩展）一脉相承：适配器就是插件。
- 用户明确的管线设计：core 收集完整信息 → 构造 → 精修 → 发出。

## 嵌套结构（2026-08-09 修正，2026-08-10 实施）

插件关系是**嵌套链**（装饰器模式）。供应商壳**包裹**协议层插件：壳 init 经 `get_dependency` 取内层协议插件接口表，`build_request` 调内层构造初步请求 → 壳补供应商默认 → 产最终请求；`parse_feed` 纯透传内层解析（响应无供应商差异）。

```
core → deepseek 壳(外层) → v1-messages 协议层(内层) → 初步请求 → 壳补默认 → 最终请求 → core 发出
     ← SSE 解析（协议层，纯透传回 core）
```

用户原始表述："第三步的精修请求的插件需要嵌套第二层的初步构造的插件"。2026-08-10 实施时定型：壳的"精修"退化为**默认兜底**（无供应商有真正的请求改写需求，详见"协议/供应商拆分"），故 `parse_feed` 不再精修而纯透传。

## 组装机制（2026-08-09，2026-08-10 实施）

插件在元数据中**声明前置插件依赖**（供应商壳声明 `deps: ["v1-messages"]`），core 按拓扑序加载（协议层先，壳后），插件 init 中经 `get_dependency` 取内层接口表完成注入。组装关系由声明驱动、core 执行注入，插件不做运行时查找。

候选对比：
- **core 依赖注入组装（选定基础）**——插件只导出自身接口，core 按声明接线。插件可独立测试、可复用、无运行时查找。
- **插件运行时互查**——core 维护注册表 + 查找 API，插件自行查找调用。灵活但隐式耦合，测试难。
- 实际选择为**两者结合**：插件元数据声明前置依赖，core 按声明自动组装注入（用户："需要声明前置插件, 其余1"）。

## 响应解析（2026-08-09）

协议层插件**成对**提供请求构造与响应/SSE 流解析——一个插件是一个完整协议适配器。解析出的结构化事件（文本增量 / thinking 三帧 / tool_use / 停止原因）通过 C ABI 回传 core。core 保持零协议知识。供应商壳对解析**纯透传**（响应格式是协议固有的，无供应商差异）。

候选对比：
- **插件成对负责构造 + 解析（选定）**——core 完全不碰协议，与 ADR-0004 彻底一致；C ABI 需定义结构化事件传递接口。
- **core SSE 骨架 + 插件字段映射**——core 有最小协议知识（不零知识）。
- **先非流式，流式后补**——TUI 打字机效果第一版缺失。

## 首版验证（2026-08-09）

DeepSeek Anthropic 兼容端点（`api.deepseek.com/anthropic`）**完整支持工具调用与流式**：tools 字段、tool_use / tool_result 块全支持；tool_choice 四模式全支持；stream 全支持。关键细节：**`cache_control` 被忽略**——正好验证"首版不单独实现 vendor 精修层"的推断（DeepSeek 走标准 `/v1/messages` 字段即可，缓存字段直接被忽略）。

## 协议/供应商拆分（2026-08-10）

`/v1/messages` 是一种**协议**，不是某家公司的私有物——Anthropic、DeepSeek、OpenRouter 等多家公司都实现同一端点。原先单一 `deepseek-messages` 插件把"懂协议"与"懂 DeepSeek"混在一起，违反"好品味":消除不了第三家供应商除非复制整套协议代码。

**拆成嵌套链两层**（ADR-0004 原本就预留的嵌套结构）：

- **`v1-messages`**（内层，协议层）：唯一懂 `/v1/messages` 的插件。请求构造 + SSE 解析 + thinking 块都是协议固有内容。不识别任何供应商、不设端点/模型默认值。新增第二家供应商时此插件**零改动**。
- **`deepseek`**（外层，供应商壳）：薄壳，`deps: ["v1-messages"]`。init 经 `get_dependency` 取内层接口表；`build_request` 调内层构造初步请求→壳补 DeepSeek 默认端点/模型/凭证→产最终请求；`parse_feed` 纯透传（响应解析无供应商差异）。**不做模型映射**——`claude-*` 原样透传，供应商特殊逻辑一律不进壳。

core 按依赖序加载（协议层先，壳后），agent 选"未被其他协议插件依赖者"为链入口（`find_protocol_plugin`）。新增第二个供应商只写新壳、复用协议层；core 据依赖自动选入口。这与"core 不内置任何具体协议/供应商知识"一脉相承。

> ⚠️ **"core 据依赖自动选入口"已被 ADR-0011 取代（2026-08-15）。** 依赖图推导出的归属取决于目录扫描顺序与图形状，是静默仲裁；`find_protocol_plugin` 还是 O(n²)。现改为：壳在 init 中 `claim(内层名)` 显式接管（被接管者退出候选集），**哪个壳进协议槽由配置 `provider` 显式指定**。多个壳互为兄弟而非层叠——各自 claim 同一个协议层。本节其余内容（嵌套结构、壳只兜底不改写、协议/供应商拆分）不变。

## 组装机制的实际落地（2026-08-10）

`get_dependency(name, &api, &inst)` 落入 core API：插件 init 中取前置插件接口表，链内包裹由插件自行完成（壳调内层）。core 只暴露查表能力，不替插件做调用编排。"声明驱动 + core 注入"落地为：插件声明 `deps`→core 按拓扑序加载→`get_dependency` 注入内层。

## 后果

- 请求构造与**响应解析必须成对**，且归属于协议层（供应商壳纯透传解析）。
- 供应商壳是独立于协议层的薄层，职责仅"供应商身份 + 默认兜底"。允许"同一协议、不同供应商"复用，新增供应商不复制协议代码。
- 交付两层协议插件（`v1-messages` + `deepseek` 壳）；其余供应商壳按需追加，协议层不动。
- 协议插件的 api_key / base_url / model 由 core 统一注入（见 CONTEXT.md 配置机制），base_url 与 api_key 同级可配；供应商默认值下沉到壳，协议层无默认。
